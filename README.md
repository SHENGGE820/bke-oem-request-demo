# BKE 代工需求管理系統｜前台測試版

這是一套把紙本「需求表單」轉成線上協作流程的操作原型，主要使用者為業管、營養師／研發與主管。

目前線上展示：<https://bke-oem-request-demo.daoson-tw.chatgpt.site/>

> 現階段是公開的前台操作展示，請勿輸入真實客戶、配方、報價或其他機密資料。

## 為什麼要做

原本的作業需要列印紙本，由業管與客戶對焦後交給營養師。常見問題包括：

- 資料散落在紙本、訊息與不同檔案，容易遺漏。
- 條件不完整時，營養師必須反覆追問與修改報價。
- 無法即時知道案件由誰處理、卡在哪裡、下一步輪到誰。
- 配方調整、打樣與結案紀錄缺少統一版本。
- 主管難以掌握逾期、退回原因與整體案件量。

目標不是單純把 Excel 搬到網頁，而是建立一個「容易填、能防呆、三方同步、可追蹤、可匯出」的案件系統。

## 使用流程

1. 業管先與客戶確認需求。
2. 業管建立案件，依引導完成需求表並送交營養師。
3. 營養師接案；資料不足時直接退回補件。
4. 營養師建立初步配方，最多保留三次配方調整紀錄。
5. 進入打樣流程，最多保留三次打樣申請與研發回覆。
6. 業管追蹤客戶，記錄是否成單、最終配方編碼與結案日期。
7. 主管從總覽查看案件量、停留階段、逾期與退回原因。

## 目前頁面

- `preview.html`：案件工作台、狀態統計、案件列表與新增需求入口。
- `wizard.html`：業管用五階段引導表單，包含防呆、條件式欄位與草稿保存。
- `case.html`：需求摘要、營養師收案、初步配方、三次調整、三次打樣及追蹤結案。
- `tasks.html`：依業管、營養師、主管角色切換的待辦展示。
- `reports.html`：主管進度概覽、逾期案件與測試 CSV 匯出。
- `build-static-preview.mjs`：將上述頁面包成 Sites 可部署的靜態服務。

## 表單已納入的重點

- 原始表單第 1–30 列的業務流程已分散到新增需求與案件處理頁。
- 目標族群可複選，選擇族群後再選對應年齡區間。
- 調理部位與期望調理方向使用色彩與表情符號幫助快速辨識。
- 調理部位、調理方向與特殊條件可複選，並支援「其他」補充說明。
- 產品每盒內容數量、單位與預計每盒售價分開填寫。
- 劑型會顯示對應規格欄位，例如粉劑、膠囊、錠劑、液態與果凍。
- 配方方式包含全營養師開發、指定原料、客供配方與仿樣。
- 檢附資料為選填，不會因為沒有附件而無法送出。
- 特殊需求包含素食、無香料、無人工甜味劑、出口、HALAL、授權、專利原料等。
- 送出前提供完整摘要；必填欄位與複選群組有防呆提示。

## 目前資料狀態與限制

這版是可操作的「前台原型」，不是正式多人系統：

- 畫面上的案件、客戶與報表數字都是測試資料。
- `wizard.html` 的草稿只保存在該瀏覽器的 `localStorage`，鍵名為 `bke-a-form-draft-v2`。
- 草稿不會跨裝置，也不會同步給其他人。
- 送出表單只呈現成功畫面，尚未真正建立共享案件。
- 附件只會讓使用者選檔，尚未上傳或儲存。
- 案件、待辦與報表尚未連接真實資料庫。
- 尚未建立正式登入、角色權限、通知、稽核紀錄與版本鎖定。
- CSV 匯出目前使用頁面內建測試資料。

## 已確定的產品原則

- 前台要讓一般同事看得懂，不呈現資料庫欄位或工程術語。
- 每個人只看到目前與自己有關的工作。
- 必填只保留會影響第一次配方或報價的關鍵資料，其餘可後補。
- 退回補件要標明缺少內容，避免另開訊息追問。
- 配方、報價、調整與打樣都歸在同一案件，不能散落成多份檔案。
- 正式版不可公開，應限制公司成員或指定帳號登入。
- 正式資料必須集中在雲端資料庫，不能依賴瀏覽器本機草稿。

## 建議下一階段

優先順序如下：

1. 確認正式資料庫與登入方式；建議使用雲端 SQL／Postgres，而不是把 Excel 當主資料庫。
2. 建立案件、使用者、角色、配方版本、打樣、附件與活動紀錄等資料表。
3. 將 `wizard.html` 送出功能改為真正建立案件，並支援跨裝置草稿。
4. 把 `case.html` 的營養師、配方與打樣操作接上資料庫。
5. 依登入角色產生真實待辦、狀態與主管報表。
6. 加上附件上傳、通知、匯出 Excel／PDF、權限與操作紀錄。
7. 用 3–5 筆匿名測試案件跑完整流程，再邀請業管與營養師試用。
