# BKE 代工需求管理系統｜前台測試版

這是一套把紙本「需求表單」轉成線上協作流程的操作原型，主要使用者為業管、營養師、研發、行銷顧問與主管。

目前線上展示：<https://bke-oem-request-demo.daoson-tw.chatgpt.site/>

> 現階段是公開的前台操作展示，請勿輸入真實客戶、配方、報價或其他機密資料。

## 為什麼要做

原本的作業需要列印紙本，由業管與客戶對焦後交給營養師。常見問題包括：

- 資料散落在紙本、訊息與不同檔案，容易遺漏。
- 條件不完整時，營養師必須反覆追問與修改報價。
- 無法即時知道案件由誰處理、卡在哪裡、下一步輪到誰。
- 配方調整、打樣與結案紀錄缺少統一版本。
- 主管難以掌握逾期、退回原因、停留時間與整體案件量。

目標不是單純把 Excel 搬到網頁，而是建立一個「容易填、能防呆、角色交棒、可追蹤、可匯出」的案件系統。

## 三種需求表的工作模式

### A｜客戶配方需求：循序交棒

A 表固定依序進行，不允許後續角色提前操作：

1. 業管完成客戶需求確認。
2. 營養師進行配方評估與報價。
3. 營養師完成後，才解鎖研發樣品打樣。
4. 研發完成後，才解鎖業管客戶確認與結案。
5. 全部工作完成後，案件狀態為「已完成」並鎖定。

A 表角色待辦、首頁與主管工作量只顯示「目前已解鎖」的工作，但 `case.html` 仍可查看完整工作鏈。

### B｜產品資料需求：並行承辦

B 表依實際需求自動建立工作，例如：

- 成分明細表
- 產品單張
- 彙辦單
- 包裝校稿
- 商標授權
- 認證／查驗登記
- 原表其他服務所對應的行銷顧問工作

B 表工作可並行處理，不因其中一項退回補件而凍結其他工作。

若原表勾選「確認無需求，可直接歸檔」，且沒有其他實際工作，案件會直接完成，不建立假的待辦。

### C｜行銷顧問需求：並行承辦

C 表依實際填寫內容建立工作，例如：

- 官網產品審稿
- 產品介紹 PPT
- 教育訓練 PPT
- 外出教育訓練

同一案件可同時存在多個行銷工作，全部完成後案件才完成。

## 退回補件流程

共用案件已支援真正的補件往返，不只是畫面文字：

1. 目前承辦角色可將未完成工作退回業管補件。
2. 系統保存原承辦角色／人員。
3. 該工作改由案件申請業管負責，狀態為「等待補件」。
4. 業管完成補件後，以「完成補件並送回原承辦」交回。
5. 工作回到原承辦，狀態變為「等待確認」。
6. 不會因補件完成而誤跳到下一工作階段。

此規則可用於 A、B、C 的共用案件工作；A 仍受循序解鎖限制，B／C 其他並行工作可繼續進行。

## 案件狀態規則

案件總狀態由目前工作自動推導：

1. 有工作等待補件 → `退回補件`
2. 否則有工作等待確認 → `等待確認`
3. 否則仍有未完成工作 → `進行中`
4. 全部工作完成 → `已完成`

逾期是獨立條件，不會覆蓋補件語意。首頁可同時把同一案件列入「退回補件」與「已逾期」篩選。

## 完成鎖定

共用案件完成後會鎖定：

- 已完成工作不能再修改。
- A 表尚未解鎖工作不能提前修改。
- 整案已完成後，共用 store 不允許一般更新把案件重新打開。
- 正式版若要支援重新開案，應由具權限角色另外設計「重新開啟案件」操作，不應靠直接改工作狀態。

## 活動與事件紀錄

除了舊版文字 `activities`，共用資料層已開始保存結構化 `events`。目前事件包含：

- `case_created`：建立案件
- `owner_changed`：負責人／角色變更
- `status_changed`：工作狀態變更
- `due_changed`：期限變更
- `note_added`：工作更新備註
- `supplement_returned`：退回業管補件
- `supplement_resumed`：補件完成送回原承辦
- `case_completed`：案件完成

事件會保存前後值，例如：

- 負責人：A → B
- 狀態：進行中 → 等待補件
- 期限：原日期 → 新日期

`case.html` 最近活動會優先顯示結構化事件；角色待辦也會顯示近期事件。

## 期限、逾期與停留時間

- 工作有期限、尚未完成，且期限早於瀏覽器本地今天日期時，判定為逾期。
- 日期使用瀏覽器本地日期，不使用 UTC 日期字串判斷，避免台灣時區跨日誤差。
- `case.html`、`tasks.html`、`preview.html`、`reports.html` 共用同一套逾期判定。
- 主管頁會顯示逾期案件、目前工作停留天數與最長停留案件。
- B／C 多項並行時，可顯示其中幾項逾期。

## 完成率

共用 store 提供案件工作完成率：

`已完成工作數 ÷ 全部工作數`

A 表有一個重要規則：

- `BKECases.all()` 為角色／首頁使用的 staged view，只曝露目前可執行工作。
- `BKECases.find(id)` 回傳完整 raw case，包含 A 表完整工作鏈。
- **任何 A 表完成率、事件數、完整工作數統計，必須用 `find(id)` 的 raw case 計算，不能直接用 staged view。**

B／C 因為工作本來就是並行，`all()` 會保留所有未完成工作。

## 表單已納入的重點

- 原始表單第 1–30 列的業務流程已分散到新增需求與案件處理頁。
- A 表引導版與快速版均已建立。
- B 產品資料需求表與 C 行銷顧問需求表已建立。
- 目標族群、調理方向與特殊條件等複選欄位依既有表單保留。
- 劑型會顯示對應規格欄位。
- 檢附資料為選填，不會因沒有附件而阻擋測試送出。
- A／B／C 表送出後會建立共用本機測試案件。
- B／C 會依實際提出需求建立對應工作，不自行加入原表不存在的服務選項。
- 建案加入短時間重複提交保護，避免快速雙擊建立兩筆相同案件。

## 目前資料狀態與限制

這版是可操作的「前台原型」，不是正式多人系統：

- 共用測試案件使用 `localStorage` 鍵 `bke-demo-cases-v1`。
- `wizard.html` 草稿鍵為 `bke-a-form-draft-v2`。
- `wizard-simple.html` 草稿鍵為 `bke-a-form-simple-draft-v1`。
- B、C 表各自使用獨立本機草稿。
- 草稿與案件都不會跨裝置，也不會同步給其他人。
- 附件只會讓使用者選檔，尚未上傳或永久儲存。
- 尚未連接共享資料庫。
- 尚未建立正式登入、角色權限、通知、多人衝突處理與伺服器端稽核紀錄。
- 現在的「完成鎖定」是前端／localStorage 原型保護，不等同正式權限鎖定。
- 事件紀錄目前存在瀏覽器 localStorage，正式版應搬到後端 append-only audit/event table。

## 已確定的產品原則

- 前台要讓一般同事看得懂，不呈現資料庫欄位或工程術語。
- 每個角色只看到目前與自己有關、已解鎖的工作。
- A 表循序交棒；B／C 依實際需求並行。
- 退回補件必須清楚交給業管，補完後回到原承辦。
- 配方、報價、調整、打樣、資料需求與活動歷程都歸在同一案件。
- 不新增原始工作簿沒有的表單選項。
- 正式版不可公開，應限制公司成員或指定帳號登入。
- 正式資料必須集中在共享資料庫，不能依賴瀏覽器本機資料。

## 建議下一階段

1. 確認正式資料庫與登入方式，建議使用雲端 SQL／Postgres。
2. 將案件、工作、事件、使用者、角色、配方版本、打樣、附件拆成正式資料表。
3. 把目前 `events` 模型搬成後端不可任意覆寫的事件／稽核紀錄。
4. 建立真正的角色權限與「重新開案」權限，而不是讓完成案件任意改狀態。
5. 建立跨裝置草稿、附件上傳與通知。
6. 加入多人同時更新的版本控制／衝突處理。
7. 用匿名測試案件跑完整 A、B、C 與補件／逾期／結案回歸，再邀請實際業管、營養師、研發與主管驗收。
